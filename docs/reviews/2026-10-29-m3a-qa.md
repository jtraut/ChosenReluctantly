## 2. The recurring flake: cause found, the test was wrong

`slice6_qa_test > test_f1_same_seed_crowd_is_bit_identical_across_runs_and_shifted_instance_ids`.

Evidence:
- It fails only inside the full suite (never alone, never with its own suite alone). In runs 1 and 2 the failure text was bit-identical (enemy 0: `(-0.144992, 0.000941, 1.766786)` vs `(-0.144935, 0.000941, 1.766769)`), differences of 1e-5 to 7e-4 m. Always first run vs second; second equals third.
- Instrumented runs (temporary prints, since removed) showed the same 300 physics ticks per crowd, an empty enemy roster and `Engine.time_scale` 1.0 on every tick. So not hit-stop, tick count or leftover enemies (C1-t's theory is not what is happening now).
- Decisive experiment (throwaway test, removed): same seed, same game code, but allocating 0, 1, 2, 5, 13 or 40 unrelated `StaticBody3D` nodes before the run. Worst position difference: 0, 7.8e-4, 0, 7.8e-4, 0, 0 m. One unrelated physics body changes the settled crowd by 7.8e-4 m. The physics server's pair ordering depends on its handle allocation history, which depends on when earlier tests' deferred frees landed. That is engine behaviour, not game non-determinism. The game's real determinism guarantees (sim hashes in fresh processes, `seeded_sim_repeat_test`) are unaffected.
- Not proven: which engine structure reorders. The experiment shows the dependence, not the mechanism.

Fix (`tests/unit/slice6_qa_test.gd`): position tolerance goes from 1e-6 to `PHYSICS_NOISE = 0.01` m for first vs second and second vs third, with a comment recording the evidence. The strict pin on instance-id independence is the sibling `test_f1_steering_depends_on_spawn_index_not_on_the_instance_id` (1e-5, no physics), and an id-dependent swirl moves a crowd by decimetres, so 1 cm still catches it. The different-seed check (must differ by more than 0.01) is unchanged. The test name still says "bit identical"; left alone to avoid breaking references.

## 4. Bot sim whole-run

- `run_wave_sim.ps1 -Run -Seed 1 -Runs 12 -Scale 1`: 12/12 WON, 8 of 8 rooms, exit 0, about 13 s wall per run (fast-forwarded), 258-291 sim seconds. Generator over 1000 seeds: 5/1/1/1 per run, elite rooms 4-7 at 22-28%, rest rooms 3-7 at 16-25%. Pick rates 0.80x-1.27x, no OUTLIER or NEVER CAST.
- Same seed twice in the same configuration is identical (seed 4: byte-identical result line).
- The detectors are not vacuous. Soft lock: `-God -Idle -RoomTimeout 30` gives `ISSUE: SOFT LOCK: run 4 room 1 ... not finished after 30 sim seconds`, outcome SOFT_LOCK, exit 1; `-RoomTimeout 12` on a normal run also exits 1. An idle bot LOSES with exit 0 (a loss is not a failure, by design). N3: new tests call the sim's `_check_cooldowns` and `_begin_run_room` on constructed bad cases: negative cooldown, cooldown above its own duration, a cooldown frozen for 10 s (a healthy draining one does not trip it), an empty deck and an empty slot. All produce issues.

## 7. Findings

Blocking: none.

Non-blocking:
1. **Run-mode sim results depend on earlier runs in the same process.** Seed 4 played first: room 5 takes 32.6 s (sim 287 s). Seed 4 played after any other run (`-Seed 3 -Runs 2`, `-Seed 2 -Runs 3`, `-Seed 1 -Runs 12`): room 5 takes 28.3 s (sim 282 s). Identical at every non-first position, so a one-off shift, not drift. Likely the same physics-allocation sensitivity as section 2, but unproven (a leaked static such as `EffectTemplates._buff_serial` is not ruled out). Consequence: reproduce a batch failure with the same `-Seed` and `-Runs`, not the failing seed alone. Owner: gameplay-dev, low priority.

3. The `--run-room=8 --run-clear-after` debug launch shows "Rooms cleared 1 / 8" on the win screen because only the played room is in history. Debug-only.
