## What I tested, and how

### Generator (`tests/unit/map1_qa_test.gd`, independent of the dev's checker)

I wrote my own checker from the raw nodes and edges lists and the config numbers, without calling `MapRules` or `MapGraph`'s validators. It runs on **1000 seeds the dev's sweep never used (5000..5999)**. For every map it checks: ids unique and equal to `(room - 1) * columns + column`; every node on the grid; room 10 holds exactly one boss; rooms 1 to 9 hold 2 to 4 nodes; every edge goes to the next room and moves at most one column (the boss's room-9 edges are exempt); no duplicate edges; **no two edges between the same pair of rooms cross**; every non-boss node has 1 to 3 outgoing edges and every room-9 node leads to the boss; every node past room 1 has an incoming edge; **every node is reachable from room 1**; types match the fixed rooms, windows and weights (the weight-0 types never appear); no `no_repeat` type follows itself along an edge; fight nodes (and only they) carry a wave id that the room's list allows; only relic stages carry a chest; branching of rooms 1-8 is at least `min_branching`; and a depth-first walk of **every path** checks length 10, `min_fights`, `max_elite_like`, `max_rest`, `max_merchants`, `no_repeat`, best relic estimate inside `relic_route` and worst at most `ignore_route_max`.

- **Result: 1000 of 1000 pass, worst case well under `max_attempts`, zero failures.** Every shipped type appears across the sweep, and across 200 seeds all three chest sizes appear.
- A guard test breaks a good map four ways (an edge to a missing node, a combat swapped to an elite without a wave, a missing edge, a wave id not in the list) and requires the checker to object each time, so the checker can fail.
- **Determinism:** the same seed gives the same map twice in process; the golden hash of seeds 1 to 40 (`1128919566`) is pinned (a regression guard that says "the stream changed", not independent proof); and **a separate process** (`map_print.gd` launched with `OS.execute` for seeds 3, 11 and 777) prints every line of the map the test process generates.
- **Other valid configs:** columns 3 and 5, walks 3 and 6, and an 8-room map all validate; the generator then either gives a map that passes the checker or fails with a "MapGenerator: ..." message. It never hangs.

### Validator

- An unknown key is rejected in **every object** of the shipped config (found by walking the config, not from a hand list).
- Every leaf of the shipped config was replaced with each of 12 hostile values (null, a string, -1, 0, 1e9, 1.5, `[]`, `{}`, true, `[1]`, `[5, 2]`, `[0, 99]`). `validate` never crashed; every accepted mutation was then fed to the generator, which gave a map that passes my checker or a clean error. This is how I found carry-over 1.
- Every top-level key, when missing, fails with a message that names it. Bad windows (`[4, 3]`, `[0, 5]`, `[3, 11]`, strings, a float, wrong length) fail and name the type. The boss missing from `fixed`, or on room 9, fails.
- **Corrupt `map.json`:** eight files written to `user://` (empty, garbage text, truncated at half, an array root, a trailing comma, `rooms` as a string, an unknown top key, `enabled` as "yes") plus a missing path. `MapConfig.load_from` returns no config and a reason every time.

### Node handling, gold and the run flow

- Read the dev's `map1b_flow_test` (combat card offer plus gold, elite relic offer plus gold with the card fallback, relic stage with chest sizes and tier rows, rest, boss) and ran it green; I did not duplicate it.
- **Gold:** deterministic per seed and node, in range, independent of the order nodes are visited, 0 for boss, rest, relic stage, merchant, unknown types and for bad gold data (a string, a one-element array, an empty table), and safe for negative and huge seeds.
- **Paid once, no double pay on reload (scene level):** a real room-1 fight is won, the gold and the `gold_changed` signal match `roll_gold` exactly once, the state goes through `to_json` / `from_json`, a fresh scene is built on the restored state, and gold, offer and pending reward are unchanged, no `gold_changed` fires and the cleared room is not fought again.
- **Nothing for rooms skipped by `--run-room`:** at targets 1, 5, 9 and 10 gold stays 0, the path is exactly the first route up to the target, the state round-trips, and a target past the end clamps to the boss.
- **Map-aware versions of the m3a-style guards** (suggested by the way my four straight-run suites are pinned): pick spam moves exactly one room (three rounds over every next node: 1 accepted) and a node pick **cannot skip an open reward** (refused, state byte-identical); dying in the frame of the last kill on a map run is a loss, reports no clear and pays no gold (both orders); and a walk through nine node picks to the boss (taking a card, a relic, or the first rest option on the way) lands on room 10 as the boss, pays gold, and leaves at most one old room alive.
- **Round trip mid-map:** at every step of five full walks the pending pick survives `to_json` / `from_json` equal, with the same reachable ids; hostile option ids (`node:-1`, `node:abc`, `node:`, `card:1`, `node:99999`, empty, a node from the wrong room) are refused and change nothing byte for byte.
- **Damaged saves:** a wrong room index, a duplicated or unknown path id, a non-array path, an empty or non-string map, and a map missing its boss all drop the map and path loudly and leave a consistent straight run. A bad gold string falls back to 0 and keeps the map. Two gaps found, see carry-overs 2 and 3.
- **Launch flags:** `--map`, `--no-map`, none, every odd combination (both, either repeated, `--map=1`, `--map=false`, `--no-map=1`, empty value) and look-alikes (`--map-seed=3`, `--mapper`) behave as documented; the override beats the data switch both ways in `begin_new_run`.
- **Map off is the old run in code too:** with the override at 0 a new run has no map, no path, gold 0, `pending` none, round-trips equal, and its 10 rooms come from `RunGenerator` as before. Combined with the `-NoMap` sim numbers above, I treat "unchanged" as shown.

## Housekeeping

### c1e ghost-look flake: root-caused and fixed

`c1e_cues_test > test_the_ghost_look_lasts_until_the_player_is_clear_of_enemies` (line 199, `is_pass_through()` expected true). I could not make it fail alone (25 of 25 isolated runs passed), so I ran it with a CPU hog (28 busy processes on 24 cores): **8 of 19 runs failed**. A diagnostic copy that printed the state at the assert showed the cause on every failure: `restore_pending` false, `dist = 0.905`. The blocker chaser is placed 0.2 m inside the player, and the grant came after `await _frames(2)`. For those frames both bodies are still solid, so depenetration pushed them apart by an amount that depends on how many physics ticks ran per frame (0.797 m on passing runs, 0.905 m on failing ones). At 0.9 m or more (player radius 0.4 plus chaser 0.5) nothing overlaps when the 0.2 s buff ends, so the player never enters the "wait until clear" state the test is about. **It is a race in the test's setup, not a game bug**: the game's rule (stay non-solid until clear of enemy bodies) holds.

Fix, in `tests/unit/c1e_cues_test.gd` (routed to me by the BD2 carry-over; the assertions are unchanged, only the order): grant pass-through before the first physics tick. After the fix the same diagnostic copy passed **24 of 24 under the same load, `dist` 0.200 on every run**. The comment in the test records this.

### `w1a_test` "wizard bolt does not reach past its 12 m range": not reproduced

I could not make it fail: 20 of 20 isolated runs of `w1a_test` under the same 28-process CPU hog passed (31 cases each), and it passed in all three full-suite runs I made. I read the test: the first check (the enemy at 15 m takes no damage after 120 physics ticks) can only fail if a bolt travels past 12 m or something else hurts the enemy; I found neither path in the code. I record it as **a one-off that I can't reproduce**, not as a known flake. If ux or anyone sees it again, the failure message (which assert, with the enemy's HP) is what's needed.

## Carry-overs

Each has a **skipped** regression test in `tests/unit/map1_qa_test.gd` (`do_skip := true` with the reason). I ran each unskipped to confirm it fails today; remove the skip when the fix lands. They are not reachable with shipped data or from play today, which is why they are not blockers. Items 2 and 3 matter when MAP3 adds the save file.

1. **gameplay-dev: `MapGenerator.gd:59` script-errors when a node has no candidate type.** The line is `var problems: Array[String] = MapRules.path_problems(...) if not map.is_empty() else ["a node had no type to draw"] as Array[String]`. The `as Array[String]` on a literal does not work in the else branch, so the engine reports "Trying to assign an array of type Array to a variable of type Array[String]", `build` returns nothing, and `generate` then fails again on `result["ok"]`. Repro: copy the shipped config, set `types.combat.weight` to 0 (`MapConfig.validate` accepts it), call `MapGenerator.build(1, cfg, RunConfig.get_config())`. Expected: `{ok: false, error: "MapGenerator: ..."}` with a message. The one-line fix is a typed local first (`var no_type: Array[String] = ["a node had no type to draw"]`). The validator could also refuse a config where some room of 3 to 9 has no type whose window covers it, but the fix above is enough. Test: `test_carryover_a_config_the_validator_accepts_but_cannot_fill_fails_with_a_message_not_a_script_error`.
2. **gameplay-dev: `RunState.from_dict` keeps `pending: "node"` when the map is damaged but non-empty.** Repro: take a fresh map run's `to_dict()` (it opens on the pick, `pending` "node"), set `map` to `{"nodes": "x", "edges": []}` or append an edge `[0, 12345]`, call `from_dict`. The map fails `normalize` and is dropped, but `pending` stays "node", so the straight run is left holding a node pick with no map to pick from (an empty choice screen: a soft lock once saves exist). Empty, erased and non-dictionary maps are handled; these two cases are not. Fix: after `_read_map_fields`, if the map came out empty and `pending` is `PENDING_NODE`, set it to none. Test: `test_carryover_a_damaged_map_with_an_open_node_pick_does_not_leave_a_straight_run_holding_the_pick`.
3. **gameplay-dev: `from_dict` accepts a negative gold.** A save with `"gold": -50` loads as -50. Clamp at 0 (or refuse) in `_whole_or_zero` for gold. Test: `test_carryover_a_negative_gold_in_a_save_is_refused`.
4. **gameplay-dev: capture presets.** Add `--no-map` to `removal_screen`, `bd2_relic_elite`, `bd2_relic_room` and `bd2_relic_swap`. `removal_screen` is the worst: it now captures a combat room.
5. **gameplay-dev (tidy):** `RelicProgress.matches_of` still has the `_triggers` fallback; delete it now that `trigger_progress` exists (the tripwire test goes with it).
