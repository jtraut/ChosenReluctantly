### Blocking issue 1: orphan nodes (ux, `aa02650`)

`EnemyHpBar._ready` builds a `StatusStackLabel` and adds it with `_add_sibling_deferred.call_deferred(stacks)`. If the enemy (and so its HP bar) is freed before the deferred call runs, the call is dropped, and the new `Label3D` is never added to the tree or freed. Each such enemy leaks one node.

- Reproduction (full): `powershell -File tools\run_tests.ps1`; suites `slice5d_qa_test` (61 orphans: `test_roster_has_no_stale_or_freed_entries...` 1, `test_roster_has_no_duplicates_after_many_spawn_free_cycles` 60) and `slice6_qa_test` (10 orphans, `test_f1_steering_depends_on_spawn_index_not_on_the_instance_id`) report them; exit code 101.
- Reproduction (isolated): `bd3a_qa_test.gd > test_an_enemy_freed_in_its_spawn_frame_leaves_no_orphan_node` (committed as a skipped probe; with the skip removed it fails with "20 orphan nodes left by 20 enemies freed in their spawn frame").
- Fix direction (not mine to write): create the label inside the deferred function (so nothing exists if the bar is gone), or add it as a sibling synchronously, or free it when the bar leaves the tree. Un-skip the probe with the fix.
- Real-game impact: a leaked `Label3D` per enemy that dies in its spawn frame (rare in play, common in the sims' spawn and free cycles). PL2 set the precedent that exit 101 from orphans is a blocking gate failure (`docs/reviews/2026-10-30-pl2-qa.md`).

### Blocking issue 2: Fire share for the Bleed bot (acceptance line)

`powershell -File tools\run_offer_report.ps1` (plain, 1000 seeds, 18 offers, shipped `status_lean` 0.25, `status_lean_skip_starter` true, D47 rule):

| Bot | Fire early / mid / late | Bleed early / mid / late |
|---|---|---|
| neutral (lean 0 and 0.25 identical) | 30.0 / 30.8 / 29.8 | 18.4 / 18.4 / 18.4 |
| Bleed-picking, Burn-pruning, lean 0 | 30.9 / 32.5 / 31.6 | 16.0 / 10.8 / 8.3 |
| **Bleed bot, shipped lean 0.25** | **29.9 / 31.7 / 31.6** | 17.9 / 13.2 / 8.2 |
| Bleed bot, pre-D47 rule (not in game) | 30.8 / 35.9 / 39.1 | 17.8 / 12.7 / 7.8 |
| Burn-picking bot, lean 0.25 | 29.8 / 26.0 / 20.6 | 18.7 / 19.7 / 20.8 |

- Neutral Fire share is 30% against the target "about 29%": met.
- The Bleed bot's Fire share does not fall over the run, and ends 1.8 points above the neutral deck. "Clearly lower over the run" is not met. D47 fixed a rise (39.1% to 31.6%) but did not produce a fall.
- Mechanism (from the numbers, not from reading the weights): the Bleed bot's own Bleed share falls from 17.9% to 8.2% because the Rogue/neutral non-Fire pool is small and the cards it owns drop to owned weight (the lean boosts unowned candidates only). The Burn bot's Fire share does fall (29.8 to 20.6) because it keeps picking Fire, which says the lean works on the pick side but cannot beat pool size on the avoid side.
- The D47 brief's "expected about 32%" was a forecast, not a re-scope of the acceptance line. Routed to game-lead as a design question (a larger or non-capped lean, a lean that also counts owned copies, or more non-Fire cards, which is MAP3b's content), not a code bug.

**Ruling on "their top damage sources differ" (BUILD_DEPTH section 2).** The vector the 0.6 distance is computed on is light, heavy, each slot type, each status, each relic. Card level is not in it, so card-level differences (Fire Wall vs Open a Vein) do not count. On that vector, relics off: both decks top out at Attack: AoE (Kindling 46%, Bleed Out 30%, with Bleed ticks a close second at 25%), so they do **not** differ. With each deck's own relics: Bleed Out tops out at `status:bleed` (31%), Kindling at Attack: AoE (46%), so they differ. I accept the with-relics reading as the one the acceptance means, because the vector includes a relic term and the archetypes are defined with their relics (the Grudge Brawler deck says it is "only viable with its relics"). On the relics-off reading the line is a near miss, and game-lead should confirm which reading is meant. Non-blocking.
