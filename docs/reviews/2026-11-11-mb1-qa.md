## 2. A mini-boss death ends the room and act, never the run

`Boss.is_mini_boss()` sets tier `mini_boss` and rank `elite`; the death beat comes from the entry's `death.beat_seconds` (1.0). The run is won by node type, not by a boss dying, and the rewards still come from the `mini_boss` node (the relic offer then the card offer, `RunController` line 458). `test_killing_the_mini_boss_ends_the_room_and_opens_the_act_end_choices_but_not_the_run` and `test_killing_the_act_two_mini_boss_ends_the_act_and_never_the_run` drive a real kill; `test_the_final_boss_room_still_wins_the_run_by_node_type` is the counterweight. HP: the spawn entries carry no `tier` (asserted), so the x3.5 tier is not applied; `Enemy.apply_act_scale` takes the act `hp`. The test for final HP reads the spawn data and the scene's boss and checks 170 and 170 x 1.1, not a full spawner path; that is enough because the only way a tier gets applied is the spawn entry's `tier`.

## 7. The `player_death_test.test_enemy_stops_targeting_dead_player` flake

**Finding: a test-setup fragility that predates MB1, not a game bug and not state leaked from a new MB1 suite. Fixed test-side. Not reproduced, so the fix is argued, not proven by a failing-before run.**

Evidence:
- It failed in two of ux's full runs (`full2.log`, `full3.log`: "Expecting to be less than 0.010000 but was 2.412000" at the velocity assertion) and passed in others; `git log` shows the test file untouched in the review range, and the test, the enemy and `collide_with_enemies` all predate MB1.
- The enemy branch under test is correct. Reading `Enemy._physics_process`: with a dead player the stand-down branch sets `velocity.x/z` to `_knockback_velocity` (zero for a fresh enemy) and drops the wind-up, which the test's first assertion shows happened. Nothing in that branch chases. Only `move_and_slide()` after it can change the velocity, so a 2.412 sideways velocity comes from the physics step, not from the AI.
- The test spawned the enemy at the origin, inside the player's capsule (both are solid to each other, `body.collide_with_enemies` true). A probe suite (not committed) showed what that does: the enemy stands on the player's head and, in 40 physics frames, the pair climbs to y about 53 with no limit, and with partial overlaps the bodies slide apart by an amount that varies from run to run. A slide-out velocity is the only plausible source of the 2.412 sideways velocity.
- Ruled out as the cause: leftover slow-mo or time scale (probes at `Engine.time_scale` 0.3 and 0.05 gave velocity 0), so ux's `7897d66` reset is harmless but is not the fix; and a state leak from a new MB1 suite (the three MB1 suites plus `player_death_test` run together passed: 102 cases, 0 failures).
- I could not reproduce the 2.412 in isolation, in that subset, or in my full runs (below). I say so plainly.

Fix (test only, `tests/unit/player_death_test.gd`): the enemy now starts 4 m from the player so no pair overlaps, and the velocity assertion carries a failure message with the velocity, knockback, both positions and the stun flag, so a future failure names its cause. The assertion itself is unchanged (still under 0.01), not weakened.

**Non-blocking carry-over (gameplay-dev, not MB1):** two co-located solid bodies climb without bound (the probe showed y about 53 after 40 frames). A spawner never places an enemy on the player, and the sim's `climb:` line watches this, so it is not a play bug today; it is why the old fixture was fragile.

## 8. Code review (typed, data-driven, no leaks)

- **Typed GDScript:** every new function carries a return type and the new vars are typed. One style nit: `for enemy in _enemies:` in `Scenario.gd` has an unannotated loop variable (non-blocking).
- **Data not code:** attacks, phases, chains, the `mini_boss` marker, counts, scatter, act tints, the chain-cue format, the subtitle and the detonate-word text are all data (`bosses.json`, `run.json`, `ui.json`); the chain cue and the "Wants X stacks" word are derived from the data, not a card or attack id. - **Node leaks:** the wedge's dark band is built only for boss wedges (c229682); the suite reports 0 orphans (section 6).
- **Performance:** `StatusStackLabel._process` calls `get_nodes_in_group` and `String.split` for each visible label each frame, which is O(n^2) in visible labels. Fine at today's enemy caps; note it if the cap grows (non-blocking). `Boss._aoe_centers()` allocates a one-element array per call for a single disc, and the sim calls it per frame; negligible.
