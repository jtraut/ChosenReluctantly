## Verdict on sitting 1: FAIL (one blocking issue, a one-line fix)

**Blocking: `tools\run_wave_sim.ps1` exits 1 on every run that uses a bot preset with a nonzero aim error.**
- Reproduction: `powershell -File tools\run_wave_sim.ps1 -Seed 1 -Seconds 10 -BotPreset human; echo $?` prints `WAVE SIM OK`, then `Engine errors/warnings in output:` followed by the line `Bot settings: human (reaction_delay 0.20 s, aim_error 25.0 deg, ...)`, and exits 1. Same for `-BotAimError 10`. Without a preset the exit is 0.
- Cause: line 80 of the script filters the output with `-match "ERROR|WARNING"`. PowerShell `-match` is case-insensitive, so the sim's own `aim_error` text matches. The sim result itself is fine (all 22 human `-Run` jobs and 3 human arena runs below ended `WAVE SIM OK`, and I grepped every output for real `ERROR`, `WARNING` and `SCRIPT ERROR` lines: none).
- Why the tests missed it: `sim1_bot_settings_test` launches Godot directly (`WaveSim.tscn`) and never goes through the `.ps1`. The documented command is the `.ps1`.
- Impact: MB1 is to gate on the `human` preset through this script, so every gate run would read as a failure.
- Suggested fix (gameplay-dev; I did not touch the script): match engine prefixes case-sensitively, for example `-cmatch '^\s*(SCRIPT )?ERROR:|^\s*WARNING:'` (check against what the engine really prints), rather than renaming the print, so the next lowercase "error" in a log line does not re-trigger it.
- Regression test: `tests/unit/sim1_qa_test.gd` (3 cases, runs the `.ps1` through `OS.execute`). Run alone before the fix: `test_wave_sim_script_exits_zero_with_the_human_preset` FAILED, `..._with_the_sweep_overrides` FAILED, `..._with_the_default` PASSED (control). **Committing it makes the full suite red (2 failing cases) until the fix lands. That is the regression test working, not a regression.** The suite figure below (2095, exit 0) was taken without it.

Everything else in sitting 1 is sound:
- **Default is off:** `data/bot_presets.json` `default: "off"`, all zeros; `is_active()` false takes the unchanged code path. `-BotPreset off` gives the same hash as no flag (3172486861).
- **Seeded RNG only:** `HumanBotFilter` has one `RandomNumberGenerator`, seeded in `reset()` from `run_seed * 7919 + 31 (+ room index)`. No `randf()` or `randi()` calls outside it (grep). The run also repeats exactly: `-BotPreset human -Seed 1 -Seconds 30` gave state_hash 2845422041 twice (separate processes); seed 2 gave 869345265. And all six human three-act cells below reproduce gameplay-dev's numbers exactly.
- **Validation fails loudly:** missing file, missing `off`, negative, NaN, over-cap and unknown-field cases are tested; an unknown preset exits nonzero in both sims.
- **Code quality:** typed GDScript throughout, small and readable. Non-blocking nits: `--bot-delay=abc` parses to 0.0 silently (`float()` of junk), so a typo in a sweep reads as "off"; `bot_sim.gd` prints `bot preset ''` in its note when no name was given and the file default is active (cosmetic).
- **Bot sim with the preset:** `run_bot_sim.ps1 -Rooms 20 -Seed 3 -BotPreset human` gives checksum 3476063471 and exit 0, so the preset is a no-op there, as documented.

## Observations for game-lead

- **Boss time moves differently per class.** Human Wizard boss times are 50-70 s (inside the 50-80 s target); human Rogue is 35-43 s (below it). The SIM1 triage said no setting moves boss time much; that holds for the Rogue and not for the Wizard.
- **The Wizard is far more sensitive to the preset** (Rogue 97% to 72%, Wizard 81% to 42%) and its seed spread is wide (7 / 6 / 2). Seed 25 at 2/12 against 7/12 looks wide but is ordinary binomial noise at p of 0.42 (P of 2 or fewer in 12 is about 7%, and one of three seeds landing that low is about 19%; chi-square on 7/6/2 is about 4.8, p about 0.09), so I do not claim overdispersion; three seeds are too few to tell.
- Human Rogue on the relic route and the safe route both win 9/12, the same as the first route's average, so neither route is clearly harder.

## Proposed floors (human preset unless said; pooled over seeds 1/13/25, 36 runs, `-Route first`)

The curve is steep (gameplay-dev: a 0.25 s delay gives 13/36 against 26/36 at 0.2 s) and a deterministic seed does not remove noise: any unrelated code change re-rolls the paths. So each floor sits about 2 binomial SDs under today's pooled value, and only the pooled count is gated, never a single 12-run seed.

| Gate | Today | Proposed floor | Argument |
|---|---|---|---|
| Rogue three-act, human | 26/36 (72%), SD about 2.7 runs | **at least 21/36 (58%)** | Two SD below is 20.6; 21 is inside the 50-75% target band and fails a real drop of about 14 points. |
| Wizard three-act, human | 15/36 (42%), SD about 3.0 runs | **at least 9/36 (25%)** | Two SD below is 9.1. It only catches a collapse, so it needs the off-bot floor below as well. See the per-class question under the table. |

| No-card ceiling | 0/12 on both bots, both classes | **at most 25% (GDD), gate on `off`** | A weaker bot makes "at most 25%" trivially true; the perfect bot is the conservative test. This departs from the brief's "on the human preset": game-lead to confirm. Report both. |

The human floors are the primary gate. The off-bot floors are tight secondary regression guards, not difficulty gates, so they do not reopen the DECISIONS ruling against "new floors set straight from the fixed bot".

**Question for game-lead: per-class or one floor.** The table gives per-class floors (Rogue 21/36, Wizard 9/36 on human), which accepts today's class gap: the same reason DECISIONS gave for rejecting per-class presets. Option B is one floor for both classes (for example 21/36), which the Wizard fails today (15/36), so MB1's "both classes meet SIM1's three-act floor" would block on a Wizard gap MB1 is not scoped to fix. Recommendation: A for MB1 (per-class floors, plus the off-bot Wizard guard), and keep the Wizard gap as a named finding for BD3b so it is not hidden.
